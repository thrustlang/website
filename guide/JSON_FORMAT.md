## Source And Generated JSON

The JSON files under `documentation/content/<version>/` are editable source files. They are not generated by the documentation generator.

The generator reads those source JSON files and writes generated website output under `documentation/<version>/`.

Keep this distinction clear:

- `documentation/content/**/*.json`: editable source content
- `documentation/versions.json`: editable source state for versions
- `documentation/<version>/search-index.json`: generated search output
- `documentation/<version>/**/*.html`: generated HTML output
- `documentation/<version>/social/std/*.png`: generated social card output

## File Map

The documentation system uses these JSON files:

| File | Type | Purpose |
| --- | --- | --- |
| `documentation/versions.json` | source | Lists known documentation versions, latest version, and default section. |
| `documentation/content/<version>/pages.json` | source | Stores standard library and language reference page content. |
| `documentation/content/<version>/compiler-command-line-reference.json` | source | Stores compiler command line reference content. |
| `documentation/<version>/search-index.json` | generated | Stores search entries built from the source content. |

The generated HTML files are not JSON, but they are produced from the same source JSON files.

## `documentation/versions.json`

`documentation/versions.json` controls the public version list and the latest version used by the documentation hub.

Example shape:

```json
{
  "latest": "v0.2.1",
  "versions": [
    { "id": "v0.2.1", "label": "v0.2.1 (latest)", "status": "current" },
    { "id": "v0.2.0", "label": "v0.2.0", "status": "archived" }
  ],
  "defaultSection": "language-reference"
}
```

### Fields

| Field | Type | Purpose |
| --- | --- | --- |
| `latest` | string | Version id treated as the current documentation version. |
| `versions` | array | Ordered list of versions shown by the docs version switcher and hub. |
| `defaultSection` | string | Preferred documentation section when a default section is needed. |

### Version Entries

Each item in `versions` describes one public documentation version.

| Field | Type | Purpose |
| --- | --- | --- |
| `id` | string | Stable version id, usually shaped like `v0.2.1`. It maps to `documentation/content/<id>/` and `documentation/<id>/`. |
| `label` | string | Human-readable label shown in selectors and cards. |
| `status` | string | Public status. Expected values are `current` and `archived`. |

`scripts/release_docs.py` inserts the new version at the front, marks it as `current`, and marks older versions as `archived`.

`scripts/archive_docs.py` changes a non-latest version to `archived`.

## `documentation/content/<version>/pages.json`

`pages.json` is the editable source for standard library pages and language reference pages in one documentation version.

Top-level shape:

```json
{
  "std": {},
  "language-reference": {}
}
```

### Top-Level Sections

| Section | Type | Purpose |
| --- | --- | --- |
| `std` | object | Standard library module pages, keyed by slug. |
| `language-reference` | object | Language reference topic pages, keyed by slug. |

The object key is the page slug. A flat slug like `io` generates a page under `documentation/<version>/std/io/`. A nested slug like `collections/vector` generates nested output under `documentation/<version>/std/collections/vector/`.

## `std` Section

The `std` section contains standard library pages. Each key is a module slug and each value is the page data.

Example shape:

```json
{
  "std": {
    "io": {
      "title": "std::io",
      "summary": "Input and output APIs.",
      "source": "io.thrust",
      "overview": ["High-level introduction."],
      "details": ["Behavior notes."],
      "examples": ["import std::io;"],
      "notes": ["Check return values."]
    }
  }
}
```

### Standard Fields

| Field | Type | Purpose |
| --- | --- | --- |
| `title` | string | Page title. For std pages, prefer full module names such as `std::io`. |
| `summary` | string | Short description used in cards, metadata, indexes, and search results. |
| `source` | string | Relative source file under `thrustc/std/<version>/`. |
| `overview` | array of strings | Intro paragraphs rendered in the page overview. |
| `details` | array of strings | Behavior and usage paragraphs rendered after public signatures. |
| `examples` | array of strings | Code blocks rendered as examples. |
| `notes` | array of strings | Bullet-style notes rendered near the end of the page. |

### Source Lookup

For `std` pages, `source` is not only metadata. The generator reads the matching file under `thrustc/std/<version>/` and extracts public signatures.

Example:

```text
documentation/content/v0.2.1/pages.json
source: "io.thrust"

thrustc/std/v0.2.1/io.thrust
```

The special source value `ffi/c/*.thrust` tells the generator to collect signatures from several C FFI source files.

## `language-reference` Section

The `language-reference` section contains language topic pages. Each key is a topic slug and each value is the page data.

Example shape:

```json
{
  "language-reference": {
    "types": {
      "title": "Types",
      "summary": "Primitive and built-in type forms.",
      "source": "syntax/types/",
      "overview": ["Topic introduction."],
      "semantics": ["Language behavior."],
      "guidance": ["Practical advice."],
      "signatures": "var value: s32 = 1;",
      "example": "fn main() s32 @public { return 0; }"
    }
  }
}
```

### Standard Fields

| Field | Type | Purpose |
| --- | --- | --- |
| `title` | string | Page title shown in headings, cards, metadata, and search results. |
| `summary` | string | Short description shown in indexes and metadata. |
| `source` | string | Source reference metadata. Unlike `std.source`, this is not used to extract signatures. |
| `overview` | array of strings | Intro paragraphs for the page. |
| `semantics` | array of strings | Language rules, behavior, and edge cases. |
| `guidance` | array of strings | Best-practice bullets for using the feature correctly. |
| `signatures` | string | Syntax or signature code block shown before the behavior section. |
| `example` | string | Main code example for the topic. |
| `reference_sections` | array of objects | Optional structured reference blocks. |
| `attribute_catalog` | array of strings | Optional catalog for attribute-style pages. |
| `applicability_notes` | array of strings | Optional paragraphs that explain where attributes apply. |

## `reference_sections`

`reference_sections` adds structured reference blocks to a language reference page.

Example shape:

```json
"reference_sections": [
  {
    "title": "Scalar Types",
    "intro": "Scalar values are stored directly.",
    "items": [
      "s32 is a signed 32-bit integer.",
      "u64 is an unsigned 64-bit integer."
    ]
  }
]
```

### Fields

| Field | Type | Purpose |
| --- | --- | --- |
| `title` | string | Heading for the reference block. |
| `intro` | string | Optional paragraph before the item list. |
| `items` | array of strings | Bullet list rendered under the block. |

Use `reference_sections` when a topic needs organized lists with their own headings, such as type families, operator groups, or syntax variants.

## `attribute_catalog`

`attribute_catalog` is an optional array used by language pages that catalog attributes.

Example shape:

```json
"attribute_catalog": [
  "@public - exports a symbol.",
  "@extern - binds a declaration to an external symbol."
]
```

Each string can use `name - description` format. The renderer formats the part before ` - ` as code and the rest as prose.

Use this field when the page needs a compact list of attributes or annotation-like constructs.

## `applicability_notes`

`applicability_notes` is an optional array of paragraphs used with attribute-related pages.

Example shape:

```json
"applicability_notes": [
  "Some attributes apply only to functions.",
  "Others apply to declarations that produce exported symbols."
]
```

Use this field to explain where each attribute family is valid, especially when the rules are broader than a simple catalog list.

## `documentation/content/<version>/compiler-command-line-reference.json`

`compiler-command-line-reference.json` is the editable source for compiler CLI documentation in one documentation version.

Top-level shape:

```json
{
  "title": "Compiler Command Line Reference",
  "summary": "Detailed reference for compiler command line flags.",
  "source": "thrustc/thrustc_cli/src/help.rs",
  "overview": ["Intro paragraph."],
  "usage": ["thrustc main.thrust -opt O2"],
  "categories": []
}
```

### Top-Level Fields

| Field | Type | Purpose |
| --- | --- | --- |
| `title` | string | Main title for the CLI reference index. |
| `summary` | string | Short description for cards, metadata, and search. |
| `source` | string | Source reference for where the CLI help should be checked. |
| `overview` | array of strings | Intro paragraphs rendered on the CLI reference index. |
| `usage` | array of strings | Example command blocks rendered on the CLI reference index. |
| `categories` | array of objects | Groups of related command line flags. |

The CLI JSON should stay aligned with `thrustc/thrustc_cli/src/help.rs`. Flags that exist only in parser internals are not public website documentation until they appear in help output.

## `categories`

`categories` groups related CLI flags into separate pages.

Example shape:

```json
"categories": [
  {
    "slug": "compiler-flags",
    "title": "Compiler Flags",
    "summary": "Core compilation and backend flags.",
    "intro": "These flags shape the compilation pipeline.",
    "flags": []
  }
]
```

### Fields

| Field | Type | Purpose |
| --- | --- | --- |
| `slug` | string | URL slug for the category page. |
| `title` | string | Category page title and card title. |
| `summary` | string | Short category description for cards and search. |
| `intro` | string | Intro paragraph rendered on the category page. |
| `flags` | array of objects | Flag entries rendered under the category. |

## `flags`

`flags` documents one command line flag or command alias group.

Example shape:

```json
{
  "name": "-h",
  "aliases": ["--help"],
  "takes_value": true,
  "value_syntax": "optional help topic",
  "allowed_values": ["opt", "emit"],
  "description": "Show the compiler help message.",
  "details": ["Without a topic, this prints the full help."],
  "examples": ["thrustc --help"],
  "notes": ["Topics are optional."]
}
```

### Fields

| Field | Type | Purpose |
| --- | --- | --- |
| `name` | string | Primary flag spelling. |
| `aliases` | array of strings | Alternate spellings for the same behavior. Empty array when there are no aliases. |
| `takes_value` | boolean | Whether the flag accepts a value. |
| `value_syntax` | string or null | Human-readable value shape, such as `path/to/build`, or `null` when no value is accepted. |
| `allowed_values` | array of strings | Known allowed values. Empty array when unrestricted or not applicable. |
| `description` | string | One-sentence explanation for the flag. |
| `details` | array of strings | Longer behavior notes rendered as paragraphs. |
| `examples` | array of strings | Example command blocks. |
| `notes` | array of strings | Bullet-style notes, caveats, or syntax reminders. |

## Generated JSON

`documentation/<version>/search-index.json` is generated by `scripts/docs_common.py`.

It is built from:

- `documentation/content/<version>/pages.json`
- `documentation/content/<version>/compiler-command-line-reference.json`
- public signatures extracted from `thrustc/std/<version>/...`

Do not edit `search-index.json` manually. Edit the source JSON instead and rebuild the documentation.

## How The Generator Uses The JSON

The generator code lives in `scripts/docs_common.py`.

Generation flow:

1. `build_all()` reads `documentation/versions.json`.
2. For each version, `build_version()` reads `pages.json` and `compiler-command-line-reference.json`.
3. Standard library pages read `std.source` files under `thrustc/std/<version>/` and extract public signatures.
4. The generator writes HTML pages under `documentation/<version>/`.
5. The generator writes `documentation/<version>/search-index.json`.
6. Standard library social cards are generated under `documentation/<version>/social/std/`.
7. The documentation hub is written to `documentation/index.html`.

## How The Maintenance Scripts Use The JSON

The scripts under `scripts/` edit or consume the source JSON.

| Script | JSON Behavior |
| --- | --- |
| `scripts/create_docs.py` | Adds a new page entry to `pages.json` and rebuilds docs. |
| `scripts/update_docs.py` | Updates an existing field in `pages.json` or `compiler-command-line-reference.json` and rebuilds docs. |
| `scripts/release_docs.py` | Copies source JSON from one version to a new version, updates `versions.json`, rebuilds docs, and creates the release commit by default. |
| `scripts/archive_docs.py` | Updates `versions.json` status for a non-latest version and rebuilds docs. |
| `scripts/generate_std_social_cards.py` | Reads `pages.json` and writes PNG social cards for std pages. |

## Editing Rules

- Edit `documentation/content/<version>/*.json` for documentation content changes.
- Edit `documentation/versions.json` only for version state changes, preferably through release or archive scripts.
- Do not manually edit generated HTML unless you intend to lose those changes on the next rebuild.
- Do not manually edit `documentation/<version>/search-index.json`; it is generated.
- Keep arrays as arrays even when they contain one item.
- Use `null` for absent optional scalar values such as `value_syntax`, not an empty string.
- Keep slugs stable because they become public URLs.
- Keep `std.source` aligned with real files under `thrustc/std/<version>/`.

## Common Errors

### Editing Generated Output

If you edit `documentation/<version>/...` directly, the next documentation rebuild can overwrite your change. Edit `documentation/content/<version>/...` instead.

### Missing Std Source

For `std` pages, `source` must point to an existing source file under `thrustc/std/<version>/`. If the file is missing, the build fails when extracting public signatures.

### Wrong JSON Type

Fields are type-sensitive. For example, `overview`, `details`, `examples`, `notes`, `semantics`, and `guidance` are arrays of strings. `signatures` and `example` are strings.

### Unknown Slug

Scripts that update existing pages require the slug to already exist. Use `scripts/create_docs.py` before updating a new page.

### CLI Reference Drift

The CLI reference should match `thrustc/thrustc_cli/src/help.rs`. Do not document a flag as public unless it appears in the compiler help output.
